## 1. Mission and owned paths
Make the browser never lose a tab, never hang, use bounded memory and be fast: renderer crashes/hangs on real sites -> 0, time-to-first-frame and `load` at Chromium parity or better, no leaks over long sessions. A bug is yours when the renderer process dies (SIGSEGV, V8 fatal, Rust panic, OOM), a page blocks for more than the watchdog budget, memory grows without bound, or a load/raster takes seconds where Chromium takes hundreds of ms.
Owned: `tools/fuzz/` (`run.js`, `dom-mutations.html`; new fuzzers go here), `tools/repros/stability-perf/`, new `tools/bench/` (page-load and memory benchmarks, you create it); `crates/script/src/{watchdog,runtime,snapshot,cx,state}.rs` and every `unsafe` block in `crates/script/src` (29 today: runtime.rs 12, natives/misc.rs 5, cx.rs 4, state/snapshot/modules 2 each, natives/mod.rs, canvas.rs 1 each); process supervision `crates/browser/src/lib.rs` (`TabCrashed` 495, `respawn_tab` 303) and `crates/core`, `crates/launcher` (11 unsafe); `crates/engine/src/raster.rs` (vello_cpu rasteriser); the `unsafe` in `vendor/blitz-dom` (32), `vendor/taffy` (57), `vendor/anyrender_vello` (4) (stylo's 505 are upstream: audit only what our patches touch); `.github/workflows/*.yml` (fuzz/sanitizer jobs); the README perf table.
Not yours: what a page renders (layout-css lane), JS API semantics (web-apis, dom-events), TLS/CSP (network-security). If a crash's root cause is a DOM/layout semantic bug, fix the crash, hand the semantics over in a note in the commit body.
Running elsewhere, do not duplicate: css-prefs, base href, Chrome headers, container queries, the airbnb/coursera/bing/pons layout hunt, kleinanzeigen (blank page, no crash).

## 4. How to work
Build (fresh machine: expect 30-60 min, V8 is a prebuilt static lib download; ~8 GB free needed, keep ONE `target/`, never copy it): `cargo build --profile profiling -p browser-core -p browser-launcher` (binary `target/profiling/browser`). Linux deps: `sudo apt-get install -y clang lld libfontconfig1-dev libxkbcommon-dev libwayland-dev`. `-j 3` on 4-core/16 GB machines; check `df -h` before every big build.
Tests: `cargo test --profile profiling -j 3 -p script -p blitz-dom -p engine`, `cargo test -p netstack -p common`; JS layer: `cd crates/script/js/test && npm install && cd - && node crates/script/js/test/run.js`; everything fast: `tools/check.sh --rust` (JS tests, cargo test, 8 fuzzer seeds, quick WPT subset). Fuzzer: `node tools/fuzz/run.js --seeds=50 --rounds=200 --clicks=20 --jobs=3`; reproduce one: `target/profiling/browser --headless --console "file://$PWD/tools/fuzz/dom-mutations.html?seed=S&rounds=R"`.
WPT: needs the checkout next to the repo and hosts entries (`tools/dev-setup.sh` is being written by another agent; until it exists follow tools/wpt/README.md: sparse checkout, `./wpt make-hosts-file | sudo tee -a /etc/hosts`, `./wpt serve --no-h2` kept running), then `node tools/wpt/run.js --batch --jobs=3 streams resource-timing`. Sitediff: `cd tools/sitediff && npm install && npx playwright install chromium` then `node tools/sitediff/run.js https://www.kp.ru/ https://www.rottentomatoes.com/` (README there for flags; results in its output folder; compare `sharkoMs`, `sharkoTimings`, tags).
Crash debugging: `gdb -batch -ex run -ex bt --args target/profiling/browser --headless --console URL`; the renderer is a child process (`--type=renderer`), attach with `set follow-fork-mode child` or run with the env that makes the browser spawn it in-process if available (see `crates/browser/src/headless.rs`); V8 fatals print `# Fatal error in ...` on stderr and abort. Profile: `perf record -F 999 -g -- target/profiling/browser --headless ...` then `perf report`; the profiling profile keeps line tables. Sanitizers need nightly: `rustup toolchain install nightly --component rust-src miri`.
Pitfalls: the sandbox proxy adds latency and 403s for some hosts (do not diagnose `load-failed` before retrying without proxy or on the Windows sweep); bot walls (Cloudflare, Akamai) end pages early and look like `few-elements`, not stalls; timings on a loaded machine are noise: run 3x, take medians, use `--jobs=1` for timing; WPT `keepalive`/`beacon` tests and anything touching the network are flaky (rerun before treating as regression); a running `./wpt serve` needs Python 3; ASAN builds are 5-10x slower, do not run the sitediff sweep under them; never run two cargo builds in one target dir; the main tree of others may be running, work only in your own clone/branch.

## 5. Done / quality bar
